## Codebase Patterns (Study These First)

- **MV3 sandbox.pages para avaliar codigo do usuario**: `app/manifest.json` declara `"sandbox": { "pages": ["sandbox.html"] }` que carrega `app/src/entrypoints/sandbox/main.ts`. Esta pagina roda em origem nula sem CSP estrito de extension_pages, permitindo `new Function(...)` necessario para preview de scripts JS arbitrarios. Comunicacao parent <-> sandbox via `postMessage({id, script, response})` -> `postMessage({id, ok, output|error})`. Necessario adicionar a entrada ao `vite.config.mts` (input `sandbox: path.resolve(__dirname, 'sandbox.html')`) para que o build emita `dist/sandbox.html` + `dist/sandbox.js`.
- **Runner com fallback test/prod em advancedScriptRunner.ts**: detecta automaticamente o ambiente — se `chrome.runtime?.getURL` esta disponivel (production extension), usa o iframe sandbox; senao (jsdom/dev), cai em `new Function` direto. Usa `forceDirect: true` em testes para evitar criar iframe. Usa `crypto.randomUUID()` como request ID + `Map<id, resolve>` para correlacionar respostas async via postMessage. Timeout configuravel via `RunAdvancedScriptOptions.timeoutMs` (default 5000ms). Filosofia "no fallbacks" mantida: erros sempre voltam como `{ok: false, error}`, nunca silenciados.
- **Wizard scaffolding em RuleEditor**: o componente `app/src/components/rules/RuleEditor.tsx` agora segue um padrao de 4 steps (`type` | `matcher` | `action` | `review`) com header clicavel e footer fixo. Use `STEPS`/`STEP_META` como referencia ao adicionar/alterar steps. Em modo edit, todos os steps sao clicaveis; em create, sao linearmente desbloqueados via `maxStepIndexReached`.
- **Deteccao de mudancas para confirmacao de descarte**: snapshot do draft inicial (`JSON.stringify`) eh comparado com o draft atual via `useMemo`. `AlertDialog` em paralelo ao `Dialog` principal para confirmar descarte. Pode ser reaproveitado em outros editores grandes.
- **Dialog grande responsivo**: `className="flex max-h-[85vh] w-[90vw] max-w-[60rem] flex-col overflow-hidden sm:max-w-[60rem]"` no `DialogContent` produz ~960px com cap em 90vw e altura em 85vh com scroll interno via `ScrollArea`.
- **Listagem de regras com shadcn Table**: `app/src/components/rules-lab/RulesList.tsx` usa `Table`/`TableHeader`/`TableBody`/`TableRow` com colunas Ordem (priority numero), Status (toggle), Tipo (Badge colorida via `getActionVisuals`), Matcher (URL+metodo via `getMatcherSummary`), Acao (resumo via `getActionSummary`), Atualizado e Acoes. Linhas individuais ficam em `RuleTableRow.tsx`. A coluna Ordem reflete o indice 1-based na ordem original do array `rules` (passado via prop `orderById: Map<string, number>` calculada em `RulesLab.tsx`) — alinha com a regra "primeira que casa vence" do background.
- **Visuals por tipo de acao**: `getActionVisuals(action)` retorna `iconName`/`label`/`bgClass`/`textClass`/`borderClass` consistentes em toda a UI. Usar em badges, cards e icones para que cada tipo (mock=violet, delay=amber, transform=sky, breakpoint=rose) tenha cor unica.
- **Wildcard matching em URL matcher**: padroes contendo `*` no `UrlMatcher.pattern` (modo nao-regex) sao convertidos para regex via `wildcardToRegex` em `app/src/domain/ruleMatching.ts`, escapando demais meta-caracteres. Padroes sem `*` mantem comportamento de `includes()`. O modo `isRegex: true` continua usando `new RegExp(...)`.
- **Multi-select de metodo HTTP**: `MethodMatcher.method` agora aceita `string | string[]` (array para multi-select com 'ANY' como wildcard especial). `methodMatcherCasaInput` em `ruleMatching.ts` lida com ambos os formatos. Helper `createDefaultActionForType('transform')` em `RuleEditor.tsx` agora retorna `{type:'transform', enabled:true, mode:'declarative', operations:[]}` para que regras novas comecem com a forma correta.
- **Parsing de valor JSON estrito (sem fallback string)**: ao contrario do que considerei inicialmente (try parse JSON; se falhar, usar string crua), optei por exigir JSON valido sempre — strings precisam de aspas (`"hello"`). Justificativa: aceitar `hello` como string mascara intenc?o ambigua (usuario pode estar tentando digitar JSON com erro). Texto inline orienta o usuario. Honra a regra "no fallbacks" do projeto.
- **`crypto.randomUUID()` em service worker e jsdom**: disponivel em ambos. Helper `newId()` tem fallback para `Math.random` so para ambientes legados, mas tests/runtime sempre pegam o UUID real.
- **Re-matchar regra no inspector em vez de propagar metadados via InterceptedResponse**: `RequestInspector` chama `findMatchingRuleAction(rules, {url, method, headers: request.request?.headers ?? {}, body: request.request?.postData})` quando `isWaiting=true` para descobrir a regra breakpoint que pausou o request — entao surge o `description` ao usuario. Vantagens: (1) sem schema bloat em `InterceptedResponse`, (2) sempre fresh (se o usuario editou a descricao depois da pausa, reflete imediatamente), (3) zero migracao para registros antigos. Use `request.request?.headers` (nao `request.headers` top-level) porque o quirk documentado eh que top-level header sao response headers (issue #19).
- **Input numerico controlado com validacao sem fallback**: padrao em `app/src/components/rules/DelayActionEditor.tsx` — manter `inputValue` como string local + `error: string | null`. `handleInputChange` valida via regex `/^\d+$/` e `Number.parseInt(...)` antes de propagar `onChange` ao pai. Strings invalidas (vazia, com letras, decimais, negativas) pintam erro inline + nao chamam `onChange` — alinhado com regra "no fallbacks". `useEffect([action.timeMs])` ressincroniza o input quando o pai atualiza (ex.: preset clicado recebe `timeMs` diretamente em props apos `onChange`). Para presets, usar `<Button aria-pressed/data-selected>` em vez de `role=radio` em `<button>` (a11y biome).
- **Editor de acao Mock dedicado**: `app/src/components/rules/MockActionEditor.tsx` segue o padrao dos demais editores dedicados (DelayActionEditor, TransformActionEditor) e eh delegado pelo `ActionEditor.tsx` via switch sobre `action.type`. Mantem 4 Tabs (Resposta, Headers, Body, Latencia). Presets de status (200/204/400/401/403/404/500) seguem o mesmo padrao dos presets de Delay (`<Button aria-pressed/data-selected>`). Validacao JSON do body usa `JSON.parse`/`JSON.stringify(parsed, null, 2)` builtins — o `lib/` (codemirror/jsonlint/prettier) mencionado no CLAUDE.md nao existe no repo; decisao foi nao adicionar dependencia. `JsonValidation` eh tagged union (`empty`/`valid`/`invalid+message`). O botao "Formatar JSON" fica desabilitado quando body vazio ou JSON invalido (sem fallback de "format anyway"). Body string sempre transita pro pai (mesmo invalido) para nao prender o usuario mid-edicao, mas a UI mostra erro vermelho continuamente — sem silenciamento.
- **Radix Tabs em testes**: o conteudo de tabs nao-default soh fica no DOM apos `selectTab(name)` (helper que faz `fireEvent.mouseDown` + `waitFor data-state=active`). Testes que tocam inputs em tabs Headers/Body/Latencia precisam ativar a tab antes. Padrao usado em `ActionEditor.test.tsx` e `MockActionEditor.test.tsx`.
- **Drag-and-drop nativo HTML5 em tabela de regras**: `RuleTableRow.tsx` usa `draggable={canReorder}` no `<tr>`, sem libs externas (dnd-kit nao foi adicionado). Eventos `onDragStart`/`onDragOver`/`onDragLeave`/`onDrop`/`onDragEnd` no proprio `<tr>`. `dropPosition` (`'before' | 'after' | null`) eh estado local da row computado via `event.clientY - rect.top < rect.height/2`, e renderiza `border-t-2 border-t-primary` (before) ou `border-b-2 border-b-primary` (after) como insertion indicator. `RulesList` mantem `draggingId` global e passa `onReorderDragStart`/`onReorderDrop` para cada row. Hook `useRules` expoe `reorderRules(fromId, toId, position)` que faz splice na ordem do array com ajuste do indice quando `from < to`. **canReorder** eh condicional: `sort === 'priority_asc' && search === '' && actionFilter === 'all'` em `RulesLab.tsx` — evita ambiguidade quando a ordem visivel diverge da ordem do array. Acessibilidade: `tabIndex={0}` + `onKeyDown` com Ctrl/Cmd+Arrow chama `onMove(id, 'up'|'down')` (que usa `useRules.moveRule`). **Nao use `aria-grabbed`** — eh deprecado e o TS lint sinaliza.
- **fireEvent + DragEvent no jsdom**: `fireEvent.dragOver(el, { clientY: 105 })` NAO propaga `clientY` (chega `undefined` no handler — bug conhecido do testing-library com DragEvent). Solucao: `createEvent.dragOver(el)` + `Object.defineProperty(evt, 'clientY', { value: 105 })` + `Object.defineProperty(evt, 'dataTransfer', { value: dt })` + `fireEvent(el, evt)`. Para mockar `getBoundingClientRect` em jsdom (que retorna 0 por padrao em todas as dimensoes), use `Object.defineProperty(el, 'getBoundingClientRect', { configurable: true, value: () => ({ top, bottom, height, ... }) })` — atribuicao direta `el.getBoundingClientRect = () => ...` funciona para chamadas diretas mas nao garante override em todas as paths.
- **Migracoes defensivas one-shot com flag de idempotencia**: padrao em `app/src/lib/legacyMigration.ts` ja consolidado por 3 runners (`runLegacyMigration`, `runModifyToTransformMigration`, `runEnabledBackfillMigration`). Cada runner: (1) checa um flag em `chrome.storage.local` (`legacy_migrated_at`, `modify_to_transform_migrated_at`, `enabled_backfill_migrated_at`); (2) faz a leitura/transformacao em funcao pura (`backfillEnabled` etc.); (3) escreve resultado + flag. Ate quando nao ha trabalho a fazer, marca o flag para nao re-rodar a cada startup. Funcao pura testada isoladamente, runner stateful coberto via mock do `chrome.storage`. Multiplos runners encadeados em `chrome.runtime.onInstalled` + `chrome.runtime.onStartup`. **Por que separar runners**: cada migracao tem flag proprio porque versoes do produto podem instalar primeiro X mas nao Y; se compartilhassem flag, usuarios que ja rodaram a v0.7 (legacy) nao executariam Y.
- **Switch shadcn baseado em `@radix-ui/react-switch`**: `app/src/components/ui/switch.tsx` segue o padrao dos demais componentes shadcn vendidos (Checkbox/Dialog/Tabs). Use `React.ComponentRef` (NAO `React.ElementRef` — esta deprecado no @types/react atual e gera diagnostico TS). Propriedade `data-state="checked"|"unchecked"` eh exposta automaticamente pelo Radix; usar como seletor em testes (`expect(sw).toHaveAttribute('data-state', 'checked')`). O role="switch" tambem eh natively definido pelo Radix.
- **Templates de regras curados em `domain/ruleTemplates.ts`**: modulo puro com `RuleTemplateId` (10 IDs cobrindo os 4 tipos), mapa `TEMPLATES`, `TEMPLATE_GROUPS` (organizados por tipo de acao com cores consistentes via `getActionVisuals`), e `createTemplateRule(id, baseMatcher?)` que retorna `RuleDraft`. Reutiliza `PRESETS` de `rulePresets.ts` para os mocks (helper `mockSpec`) — nao duplica nomes/descricoes. `cloneAction` faz deep copy defensivo para impedir que consumers mutem o spec original (testes especificos cobrem isso). Test-ids no welcome continuam `preset-${id}` para minimizar churn em testes existentes — vocabulario "preset/template" eh fluido nos data-testids mas a UI exibe "Usar template". `RuleEditor.applyTemplateDraft` chama `createTemplateRule` e habilita o matcher de URL antes de entregar ao wizard. Para transforms cuja edicao via UI declarativa nao cobre todos os campos (ex.: `addHeaders` no template CORS), o template ainda armazena o schema correto — o gap eh do editor, nao do template.
